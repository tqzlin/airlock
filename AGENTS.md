# Airlock - agent brief (read this first, whichever model you are)

Airlock is the internal codename for a spaceship MMO built in Unreal Engine 5.8 (C++). The marketed title may differ; never rename the module.

This file is the shared brief for every agent that works in this repo (Claude, GPT/Codex, local models). `Docs/HANDOFF.md` is the operating guide (how to build, run, test, drive the editor, prove a change works); `Docs/tasks/` holds the task briefs. `CLAUDE.md` just points here.

## Working agreement for multiple agents
- One task per branch, named `<agent>/<task>` (`astra/m3-voyage-clock`, `claude/m3-mining`). `main` is merged by the reviewing agent after `Scripts\verify-loop.ps1` and the automation tests pass. Never force-push, never rewrite `main`.
- Read the task brief's "do not touch" list before editing. If the task needs a change outside it, stop and say so in the report; do not quietly widen the scope.
- Prove it, don't assert it: every change ships with an automation test and, for anything a player can see, a PIE run driven through the console helpers with the `LogAirlock` lines and captures attached to the report (`Docs/HANDOFF.md` has the recipe).
- Report format at the end of a task: what changed (behaviour first, files second), how it was verified, what you were unsure about, anything touched outside the brief, and the exact commands another agent needs to reproduce the proof.
- Commits: small, single-purpose, message describes the gameplay effect. Content (`.umap`/`.uasset`) goes through LFS; packs are never committed.
- The editor holds a Live Coding lock: close it before `Build.bat`, reopen it after (`Scripts\run-editor.bat`, which uses PowerShell `Start-Process` so the editor never inherits your shell's output pipe - an editor started with cmd `start` from inside an agent pipeline once kept that pipeline open for hours; the MCP server auto-starts on port 8000, loopback only).

## What the game is
- Big ships are server shards. A ship's sections are joined by airlock loading screens; life-support caps population per section.
- MVP scope: a station hub plus NPC-captained, instanced ~20-minute voyages (mining, pirates, derelicts). Nothing else is in scope until the MVP loop is playable end to end.
- Gameplay is server-authoritative. Anything that affects state (position, cargo, damage, economy) is decided on the server and replicated; clients predict at most.

## Code map (Source/Airlock)
- `Airlock.h/.cpp` - module + `LogAirlock` log category.
- `Core/AirlockGameMode` - the one game mode for every level; sets pawn/controller/state classes, seamless travel on. `InitGameState` fills the section id (map name), the day seed and `bVoyageBooked`; `BeginPlay` binds every `AAirlockDoor::OnTransitionRequested` to `HandleTransitionRequested`, which sends every controller `ClientBeginTransition` (the black card) and `ServerTravel`s to the door's `TargetLevel` after `TravelFadeDelay` - only if a voyage is booked, or always when `TargetSectionId == "StationHub"` (which also ends the voyage). The travel itself is `TravelToSection(Level, SectionId, Title, Subtitle)` (card to every controller, `bArrivingByAirlock` on the GameInstance, delayed `ServerTravel`); the next level's `InitGame` consumes the flag and `ChoosePlayerStart` then prefers the section's real `PlayerStart` over the PIE play-from-here start that rides along through seamless travel. Every start choice is logged. On a ship section with a pending voyage, `BeginPlay` starts the **voyage clock** (`GameState.VoyageEndServerTime` / `bVoyageActive`, server world time), builds the captain schedule (`FVoyageSchedule::Build`) and fires each line by timer as `ClientCaptainSays`; when the clock expires `ReturnToHub()` clears the voyage and travels everyone back through the same path (`HubLevel` = the door targeting the hub, else `/Game/Maps/StationHub`). `SetVoyageSecondsRemaining` moves the clock for tests (clamped to `[0, Duration]`, non-finite ignored, past entries fire once in order).
- `Core/AgentConsoleSubsystem` - editor-only GameInstance subsystem that runs console commands dropped into `Saved/AgentConsole/commands.txt` (agents drive PIE without window focus; see `Docs/HANDOFF.md`).
- `Core/AirlockGameInstance` - owns the Slate transition card (`ShowTransition`/`HideTransition`, a viewport overlay that survives `ServerTravel`) and the `bArrivingByAirlock` flag.
- `UI/SAirlockTransition` - the card itself: black SImage + title/subtitle, `FadeTo(opacity, seconds)` through an active timer.
- `Core/AirlockGameState` - replicated section state: `CurrentSectionId`, `SectionPopulationCap`, `SectionPopulation`, `DaySeed` (days since 1970, drives the three offers), `bVoyageBooked`.
- `Core/AirlockPlayerController` - Enhanced Input built in C++ (IMC + IA_Move/IA_Look/IA_Interact as default subobjects; WASD, mouse, gamepad). No input assets exist or are needed. Voyage board: `OpenVoyageBoard`/`CloseVoyageBoard` (local UI), `ServerChooseVoyage(Type)` -> `ClientVoyageBooked`. Transition RPCs `ClientBeginTransition(Title, Subtitle)` / `ClientEndTransition` (`BeginPlay` schedules the end 1 s after arriving); `ClientCaptainSays(Line)` shows a captain caption. Console helpers for agent smoke tests (send them through the AgentConsole file): `AirlockBoard`, `AirlockBook <0-2>`, `AirlockWarp x y z`, `AirlockWhere` (logs map, pawn and view location - use it before believing a capture), `AirlockVoyageClock <seconds>` (server: seconds left on the active voyage). All of these go through unchecked Server RPCs - gate them behind a dev-cheats flag before M4 multiplayer.
- `Core/AirlockCharacter` - first-person capsule + camera (no mesh yet). Binds the controller's actions. `Interact` line-traces `InteractReach` cm.
- `Voyage/VoyageTypes.h` - `EVoyageType`, `FVoyageSpec` (type, seed, 1200 s, ship class, captain, crew cap).
- `Voyage/VoyageSchedule` - pure: `Build(Spec)` -> ordered `{AtSeconds, Line}` captain announcements (departure 0, type-specific line at 50 %, one minute at `max(0, D-60)`, docking at D; stable-sorted), `FindNextUnfiredEntry`, `TryClampRemainingSeconds`. Written by Astra (M3-1).
- `UI/CaptainLineWidget` - C++-built top-centre caption for captain lines, hides itself after ~6 s, replaced by the next line.
- `Voyage/VoyageSubsystem` - GameInstance subsystem (survives level travel): `MakeVoyageSpec` (pure, deterministic), `GetOfferedVoyages`, `RequestVoyage` (server-only; also sets the pending voyage), `HasPendingVoyage`/`GetPendingVoyage`/`ClearPendingVoyage`, `TodaySeed`.
- `Core/Interactable` - `IInteractable` (BlueprintNativeEvent `Interact(Pawn)` / `GetInteractPrompt`). The character's E-key line trace calls it on the first hit actor.
- `Station/VoyageBoard` - the departure board (kit wall panel on a stand; `Interact` opens the controller's board UI). Placed in StationHub on the Dock B platform as `VoyageBoard_DockB`.
- `UI/VoyageBoardWidget` - the departure list, built entirely in C++ (`RebuildWidget` constructs Border/VerticalBox/Buttons via `WidgetTree`; no UMG asset). `OnVoyageChosen(EVoyageType)` / `OnClosed`.
- `Ship/AirlockDoor` - the section boundary. Wears the kit door (soft refs to `SM_Doorway_Small_A` / `_A3` / `SM_Door_Small_A`; primitive fallback when the packs are absent). Server-owned `bIsOpen` replicated, leaf slides up `OpenDistance` (268 cm) over `OpenTime`. Two volumes: `ProximityVolume` (wide, opens the door) and `TransitionVolume` (thin, in the wall plane; server broadcasts `OnTransitionRequested(Pawn, TargetSectionId)`). Gating: `bRequiresBooking` (locked until `GameState.bVoyageBooked`), `bAlwaysLocked` (sealed hatch); a locked door ignores proximity and crossings and shows `LockedColour` on its `IndicatorLight`, unlocked shows `UnlockedColour`. Origin = centre of the opening on the walking surface; yaw 0 means the walking axis is X.
- `Ship/ShipGraph` - the pure ship-systems model (M3-2, Astra): `EShipModuleType` (PowerCore, CoolantLoop, LifeSupport, CargoClamps, Engines, Nav, Galley), `FShipModuleState` (Condition 0-100 -> Status Nominal >= 60 / Degraded >= 20 / Failed), `FShipLineState` (Coolant or Power line with a Fault: None/Leak/Short), `FShipGraphRates` (leak drains CoolantLoop, a short drains the line's ToModule, a Degraded/Failed CoolantLoop drifts the PowerCore, a Degraded/Failed PowerCore browns out LifeSupport and CargoClamps), `FShipGraph::Build/Tick/SetLineFault/DamageModule/RepairModule/Summary`. No self-recovery; deterministic; no UObject state.
- `Ship/ShipLayouts` - the layout table: `ShipLayouts::Find(SectionId)` returns the `FShipLayout` (module and line specs with transforms and soft mesh paths). Only `Hauler_Mk1` exists; its positions are placeholders in the ship's west hall (Y 1900 / 1220, X -6300..-4700) until the level pass moves them into the real rooms. Change positions here, never in a map.
- `Core/AirlockGameMode` (M3-2 part) - `BuildShipGraph()` in `BeginPlay` on any section with a layout: builds the graph, spawns one `AShipModule` per module spec and one `AShipLine` per line spec (outliner folder `Ship`), ticks the graph at 4 Hz *only while `bVoyageActive`*, and mirrors it into the game state (`PublishShipGraph`, only when something changed; logs `Ship <Id> <Status> cond=<n>` and `Line <Id> fault=<Fault>` on changes). API for actors, console and the Incident Director: `ShipSetLineFault`, `ShipRepairLine`, `ShipDamageModule`, `ShipRepairModule`, `ShipSummary`.
- `Core/AirlockGameState` (M3-2 part) - replicated `ShipModules` / `ShipLines` arrays with `OnRep_ShipGraph` -> `OnShipGraphChanged` multicast (also broadcast on the server after each publish). Widgets and actors read the graph from here, never from the game mode.
- `Ship/ShipModule` - replicated actor per module: kit `Body` mesh from the spec (cube fallback), `StatusLight` point light (green/amber/red by status), `Label` text render (`<Id>  <Status>  <cond>%`). Collision QueryOnly, blocks Visibility only.
- `Ship/ShipLine` - replicated actor per line, implements `IInteractable` as a *hold* interaction: prompt `Tape the leak (hold E)` (3 s) / `Patch the short (hold E)` (4 s) / empty when healthy; `LeakFX` (`PS_SteamDoor`, restarted whenever the Cascade puff finishes) while leaking, a flickering orange `ShortLight` while shorted; `OnHoldComplete` -> `ShipRepairLine`. `Ship/ShipVisuals.h` holds the shared soft-mesh-with-cube-fallback loader.
- `Core/Interactable` (M3-2 part) - `GetInteractHoldSeconds()` (0 = a press, the board) and `OnHoldComplete(Pawn)`.
- `Core/AirlockCharacter` (M3-2 part) - the hold verb: `IA_Interact` Started traces and calls `ServerBeginHold(Actor)` when the target has hold seconds, Completed/Canceled call `ServerEndHold`; the server ticks `HoldElapsed` while the target is valid, still faulted and within `InteractReach * 1.25` (out of range pauses, release resets), replicates `HoldTarget`/`HoldProgress` owner-only, calls `OnHoldComplete` and logs `Hold <Label> complete by <Pawn>`. The local pawn shows `UI/HoldProgressWidget` (prompt + bar) while it has a target.
- Console helpers for the graph (all unchecked Server RPCs like the others - gate before M4): `AirlockFault <LineId> <None|Leak|Short>`, `AirlockDamage <ModuleId> <amount>`, `AirlockRepairModule <ModuleId> <amount>`, `AirlockShipStatus` (one `Ship ...`/`Line ...` line per entry, `Ship graph empty` on the hub), `AirlockHold <ActorLabel>` (same server path as the key; logs why when rejected), `AirlockRelease`.
- `Tests/AirlockSmokeTests.cpp` - `Airlock.Voyage.SpecIsDeterministic`, `Airlock.Core.GameModeDefaults`, `Airlock.Voyage.OffersCoverEveryType`, `Airlock.Station.BoardAndDoorDefaults`; `Tests/AgentConsoleTests.cpp` - `Airlock.Core.AgentConsoleFileLivesUnderSaved`; `Tests/VoyageScheduleTests.cpp` - four schedule/clock tests (order, bounds, captain name, per-type lines, clamping); `Tests/ShipGraphTests.cpp` - 11 pure-model tests (build, leak drain, core drift, brownout, short, clearing, clamps, status changes, determinism, unknown ids); `Tests/ShipInteractionTests.cpp` - hold-E in a spawned test world (range, pause/reset, completion, competing holds, destroyed target, board stays a press). 24 tests total.
- Maps: `Content/Maps/Ships/Hauler_Mk1` is a copy of the Engineer pack's `Example_Dynamic` cargo hall with all 10 doorway slots replaced by `AAirlockDoor`s (`Airlock_ToHub` at x -6980 targets StationHub; `Door_01..09` are plain doors with no target) and `PlayerStart_Ship` just inside the exit. `Content/Maps/StationHub` (editor startup + game default map) is a copy of the Interiors pack's dressed demo hall (`ModSciInteriors/Maps/Example_Dynamic`) with the pack's blueprint doors and doorway slots at both ends replaced by `AAirlockDoor`s `Airlock_Dock_A` (x -6980) and `Airlock_Dock_B` (x -4300), plus `PlayerStart_Hub` mid-hall (lower deck). Behind each dock door is a sealed airlock chamber (`Airlocks/ChamberA|B` folders: kit floor/walls/ceiling, a 120 cd point light, and a `Chamber*_OuterHatch` AAirlockDoor with `bAlwaysLocked`). `Airlock_Dock_B` has `bRequiresBooking`; `Airlock_Dock_A` is sealed ("no vessel docked"). Both maps carry a space sky: `SpaceSky_Nebula` + `SpaceSky_Stars` (StarfieldFree blueprints at the origin, folder `Sky`), `SpaceSky_Sun` (0.8 lux cold directional), a static sky light on the engine `DaylightAmbientCubemap` at 0.25, the packs' fog thinned to density 0.003 (it was 0.02 with volumetric extinction 3.5 - it swallowed the halls once the bright inscattering colour was gone), and the PostProcessVolume exposure clamped to EV100 1..9 with fast adaptation. Rebuild recipe: `agent\queue\107-109` (hub), `123-133` (chambers, sky, lighting, collision fix).

## The MVP loop as it stands (verified in PIE through the console box)
`AirlockBoard` (or E on the board) -> pick an offer -> `ServerChooseVoyage` -> `RequestVoyage` sets the pending voyage, `bVoyageBooked` replicates -> Dock B's light turns green and it opens -> crossing the threshold fades the "CYCLING AIRLOCK" card in, `ServerTravel` 0.6 s later -> `Section Hauler_Mk1: voyage underway`, spawn at `PlayerStart_Ship`, card fades out -> walk through `Airlock_ToHub` ("RETURNING TO STATION") -> voyage cleared, back at `PlayerStart_Hub`. Without a booking Dock B stays red and locked. Aboard, the captain speaks at departure, mid-voyage, one minute out and docking; when the 20-minute clock runs out everyone is returned to the hub automatically (`Scripts\verify-voyage-clock.ps1` proves it with `AirlockVoyageClock 75`; Astra's report: `Docs/reports/M3-voyage-clock.md`). `net.AllowPIESeamlessTravel=1` is set in DefaultEngine.ini `[SystemSettings]`; TransitionMap is `/Engine/Maps/Entry`.

On the ship the systems graph is live: `Scripts\verify-ship-graph.ps1` proves seven Nominal modules -> `AirlockFault Coolant_1 Leak` + `AirlockDamage CoolantLoop 50` -> CoolantLoop Degraded, PowerCore drifting -> warp to the line, `AirlockHold Coolant_1` -> `Hold Coolant_1 complete`, fault None -> `AirlockRepairModule CoolantLoop 100` -> back through the exit, `Ship graph empty` on the hub (`GRAPH OK`).

- Purchased/claimed Fab packs live in `Content/ModSci_Engineer`, `Content/ModSci_EngiProps`, `Content/ModSciInteriors`, `Content/StarterBundle` (Season 1 bundle: Command Center = the bridge kit, Props I, Hallways, Materials & Decals), `Content/StarfieldFree`, `Content/SD_Art`, `Content/Construction_VOL2`, `Content/Warehouse_Storage` and are **git-ignored** (licence + size); `THIRD_PARTY_ASSETS.md` lists what to re-claim from Fab. - `Docs/KitStandard.md` is the measured grid: Engineer corridor kit 360 cm pitch / 480 tall, Interiors room kit 670 cm pitch / 390 wall band under a cove (~6.5 m clear), shared door standard (360-wide slot, 166 x 275 leaf). `Docs/kit-mesh-bounds.csv` has every mesh's bounds and LOD0 tris.
- Anything Airlock authors on top of a pack (levels, level instances, material instances, blueprints) lives outside the pack folders so it is versioned.
- Two documented post-import steps DO touch pack assets (see `THIRD_PARTY_ASSETS.md`): Nanite on the opaque kit meshes (VSM otherwise overflows its non-Nanite marking queue) and `remove_collisions` on the two StarfieldFree sky spheres - their collision hull contains the whole map, so every *spawned* pawn was depenetrated to X = -6.9e8 while teleports looked fine.

## Driving the editor (Unreal MCP)
- Plugins ``ModelContextProtocol`` + ``AllToolsets`` are enabled (editor-only). ``.mcp.json`` points Claude Code at ``http://127.0.0.1:8000/mcp``.
- The server is a meta-tool surface: ``list_toolsets`` -> ``describe_toolset`` -> ``call_tool(toolset_name, tool_name, arguments)``. Useful toolsets: ``editor_toolset.toolsets.scene.SceneTools`` (load level, add/find actors, save), ``...asset.AssetTools`` (exists/duplicate/save_assets), ``...object.ObjectTools`` (list/get/set properties - always ``list_properties`` first), ``EditorToolset.EditorAppToolset`` (PIE, camera, CaptureViewport), ``EditorToolset.LogsToolset``, ``AutomationTestToolset.AutomationTestToolset`` (DiscoverTests -> RunTests -> GetTestResults), ``ConfigSettingsToolset.ConfigSettingsToolset`` (Project/Project/Maps etc.).
- Actor and asset type arguments are object paths (``/Script/Engine.PlayerStart``, ``/Script/Airlock.AirlockDoor``), not short names. Asset object refs need the ``Package.Name`` form (``/Game/X/SM_Y.SM_Y``). ``load_level`` refuses when the current level *or the target* is dirty - ``save_assets`` first (a freshly ``duplicate``d level is unsaved until you do). ``delete`` of a loaded level only works after another level is current. ``editor_toolset.toolsets.programmatic.ProgrammaticToolset.execute_tool_script`` batches hundreds of calls in one round-trip (Python ``run()`` returning a dict; any inner tool error fails the whole call, so keep property reads per-class).
- Slate automation (`SlateInspectorToolset`): `Snapshot` gives lines like `textbox [pos=..] [ref=tb2]`; the editor's console box is the `textbox` right after `text "Cmd"` - `Type(ref, cmd, submit=true)` runs console commands against the PIE world, including `UFUNCTION(Exec)` helpers on the player controller. NEVER `Click` a widget found by loose text: "Close" matched "Close Unreal Editor" and shut the editor. `Windows(list/close)` by title is the safe way to dismiss a stray window (the Message Log pops on PIE).
- A programmatic script over ~2000 actors can exceed 3 minutes; `agent\lib\mcp.ps1` now waits 900 s. If the client times out the editor still finishes the script - re-inspect before assuming.
- `Type` sometimes returns false the first time (focus); retry once.
- `StartPIE` without `startTransform` spawns wherever the editor camera is (the editor's "play from here"), so a `CaptureViewport` just before PIE decides where the pawn starts; pass `startTransform` for a real player view. Give exposure 6-10 s to settle before a PIE capture, and run `AirlockWhere` - a grey/black frame usually means the pawn is somewhere else, not that the lighting is broken.
- `ObjectTools`: `get_properties` takes `properties` (a list); colours read back as lowercase `r/g/b/a` floats and only set reliably in that form; enum values are set by name (`"SLS_SpecifiedCubemap"`, `"Candelas"`); nested struct sets (`BodyInstance`, PPV `Settings`) return no error but may not take - verify in PIE. `AssetTools.exists` / `find_assets(folder_path, name, asset_type, recursive)` answer "is there a cubemap" questions. `find_actors` matches actor *class* via `actor_type`; Blueprint-derived sky/sun actors hide from class filters, so count by name too.
- Programmatic scripts: an inner tool error raises a Python exception AND marks the whole call failed (the returned dict is replaced by the error), so keep risky calls in their own `execute_tool_script`; when concatenating a shared Python prelude to a here-string, add the newline yourself (`$py = $py + "`r`n"`) or the last line fuses with the next.
- Renaming a C++ actor's root component orphans already-placed instances (their serialized ``RootComponent`` dangles, they snap to the origin and cannot be moved) - respawn them.
- Loopback-only, no auth - never expose the port. Experimental: if the editor misbehaves after a plugin update, disable both plugins in ``Airlock.uproject`` and report it.

## Code conventions
- Game code lives in ``Source/Airlock`` under feature folders (``Core``, ``Voyage``, ``Ship``, ``Station``, ``Tests``); split into separate modules only when compile times demand it. Include headers by module-relative path (``"Core/AirlockGameMode.h"``).
- Prefix: ``A`` actors, ``U`` objects/components, ``F`` structs, ``E`` enums, ``I`` interfaces (standard UE). Export with ``AIRLOCK_API``. Log with ``LogAirlock``.
- Prefer C++ for systems and Blueprints only for content glue (visuals, tuning, prototyping). Anything that must be deterministic or replicated is C++.
- Every new system gets an automation test (``IMPLEMENT_SIMPLE_AUTOMATION_TEST``) or a headless smoke test that ``Scripts\run-tests.bat`` can run.
- Never commit ``Binaries/``, ``Intermediate/``, ``Saved/``, ``DerivedDataCache/``, ``*.slnx`` (already ignored). Commit ``.uasset``/``.umap`` through LFS only.
- Small, single-purpose commits; describe the gameplay effect, not the file list. Task work goes on `<agent>/<task>` branches and reaches ``main`` through review (see the working agreement above); Claude's own maintenance commits (docs, agent tooling) may land on ``main`` directly.
